# coloyond Managed Strategies Implementation Plan

> **For agentic workers:** Use superpowers:executing-plans to implement this plan task-by-task. Do not dispatch subagents without authorization.

> **Runtime revision (10 October 2026).** This plan targets the native Kotlin + Jetpack Compose app in `apps/android`. It supersedes the earlier React Native/Expo plan with shared TypeScript packages. Task scope, order, gates and acceptance rules are unchanged; file paths, interfaces and commands are now Kotlin. Each task is tracked as a GitHub issue.

**Goal:** Let people select existing managed Solana strategy tokens, generate and share abstract expressions, and buy/sell supported tokens using Jupiter while the existing protocol handles rebalancing.

**Architecture:** One native Android app. Pure Kotlin packages hold the records, hashing, validation, protocol decoding and order validation; platform packages hold storage, rendering, intents, networking and the wallet. Symmetry is a gated first protocol adapter, read with a pinned account decoder over RPC. Jupiter provides managed market swap execution. A client-run model produces validated geometric scenes. Funds stay represented by the existing protocol's share token; coloyond deploys no program and runs no keeper or transaction service.

**Tech Stack:** Kotlin, Jetpack Compose, coroutines, Mobile Wallet Adapter `clientlib-ktx`, `web3-solana`, `kotlinx.serialization` JSON, `java.security.MessageDigest` (SHA-256), JUnit with `kotlinx-coroutines-test`. Jupiter Price v3 and Swap v2 REST APIs and the Anthropic Messages API over HTTPS. Symmetry's TypeScript SDK runs only off-device, as development tooling that produces decoder fixtures. Pin exact dependency versions in the Gradle version catalog during the Task 1 probe; do not invent versions before checking compatibility.

**Spec:** [Managed strategy cards](../specs/2026-10-09-coloyond-strategy-cards-design.md). Read it with this plan; its exact schemas, text rules, limits, identity domains, and validation rules are normative.

## Global constraints

- No new smart contracts, synthetic share mint, custody, own keepers, custom routing/auction/rebalance service, shared private API key, or hidden proxy.
- Native Kotlin Android app in `apps/android`. The Vite app stays a separately labeled prototype and shares no code with it.
- V1 financial scope: existing verified Solana mainnet vaults with 1–2 target assets; secondary-market Jupiter share-token purchase/sale only. No primary deposit/redemption fallback. V1 accepts only verified Metis orders with wallet fee payer and fully known signatures; RFQ and sponsored/extra-signer paths are disabled.
- `ManagedStrategyV2` uses `cb2:`; allocation drafts use `cbd1:` and cannot execute; old `cb1:` recipes remain view-only. Use null-terminated, versioned domain-separated SHA-256 over RFC 8785 JCS.
- Transaction version 0 only. Local default ceilings: 50 bps slippage, 100 bps impact, 100000 lamports priority fee; hard maxima: 500 bps, 500 bps, 1000000 lamports.
- Financial review reads are at most 60 seconds old and obey protocol oracle freshness; keeper staleness follows the manifest's verified 60–604800-second threshold.
- Generate scenes under a 45-second stage deadline and captions under 15 seconds; do not restart deadlines on retries. Scenes at most 32 KiB, imports at most 256 KiB, strategy-only URLs below 2000 characters.
- Captions optional: default 2–8 words, hard 12 whitespace-delimited words/80 Unicode code points of stored text, without normalization (words are maximal non-whitespace runs separated by Unicode White_Space); diversity checks against 20 recent accepted captions and six motif stems over the previous five.
- Scene renderer/layout version 1; export 1080 × 1350; artwork viewport (60,60,960,960), caption (60,1050,960,110), footer (60,1210,960,80).
- No compulsory strategy names or archetypes. Keep target weights, actual composition, NAV, market price, and executable quote distinct.

## Review focus

1. A manager changes vault settings while someone views a historical card: preserve the old expression, show a diff, and require a fresh revision before purchase (Tasks 2, 3, 7).
2. Jupiter provides a price without a transaction, or a route without Price API coverage: show truthful independent availability and never infer liquidity from NAV (Tasks 1, 3, 7).
3. An execute timeout or Android process death occurs after signing: reconcile the original action and never issue a duplicate order automatically (Tasks 1, 7).
4. Desired weights have no existing exact match: retain an explicit nonexecutable draft without inventing a vault/mint (Tasks 2, 3, 6).
5. An import contains valid hashes but unknown projection/renderer versions or another expression's strategy ID: preserve only supported view-only content and never grant execution (Tasks 2, 6).

### Task 2: Implement records, hashes, and portable validation

**Files:** create `strategy/{Schema,Jcs,Identity,Expression,Imports}.kt` and `generation/Scene.kt` (pure saved-scene contract); tests `strategy/{IdentityTest,ImportsTest,JcsTest}.kt`; load `docs/design/coloyond-strategy-identity-vectors.json` as a test resource, including preserved legacy fixtures and the scene/expression vectors added here.

**Interfaces:** `normalizeStrategy(value: JsonElement): StrategyRecord` (sealed: `ManagedStrategyV2` or `AllocationDraftV1`); `strategyId(record): String`; `validateExpression(value: JsonElement, strategyId: String): ExpressionV1`; `parseImport(bytes: ByteArray): ImportedCard` returning `ImportedCard(strategy, strategyId, configurationSnapshot, expression, capability)`, where `capability` is `INSPECT` or `VIEW_ONLY`. Import never returns an executable capability. `INSPECT` means a structurally supported managed revision or draft that can be reverified or explicitly matched later; `VIEW_ONLY` means legacy/unsupported-version content whose financial use is forbidden. Configuration snapshots use the supported pinned mapping, recompute the digest, and are persisted beside the revision. `ManagedStrategyV2`, `AllocationDraftV1`, and `ExpressionV1` are exactly the spec's records. `ImportedCard.strategy` also permits a validated legacy `StrategyV1`, always view-only. Implement `validateScene(value: JsonElement): SceneSpecV1` here so saved-expression imports are complete before inference work in Task 4.
