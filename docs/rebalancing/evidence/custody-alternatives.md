# Sprint 0C — custody alternatives

**Research date:** 10 October 2026
**Base revision:** `c142f14b768cf02707d33a96e30d00d2bf020e2b`
**Status:** read-only architecture comparison; no chain transaction/signing performed. This is not an audit, deployment verification, or integration test.

## Decision

Keep the plan's **minimal Coloyond Anchor vault plus permissionless bounded auction** as the default. Reserve Folio Solana is the strongest existing custody/auction alternative and deserves a local CPI proof, but it does not currently pass the full acceptance contract on the available evidence. It can become the preferred core only if a proof shows that a Coloyond controller PDA can safely enforce the exact Pyth predicate and bounded policy, redemption meets the in-kind exit requirement atomically, fee/bounty reserves can be controlled under the required ledger rules, and the pinned deployed binary matches the reviewed source. Until then, do not base the core on it.

This decision is **conditional, not a conclusion that custom code is safer by default**. An existing core reduces implementation surface only when its built-in authorities, accounting and settlement semantics satisfy this exact product. Reusing Folio auction math or SVS accounting patterns is reasonable after license and code review; wrapping another protocol's shares would leave material custody, exit, fees and upgrade trust outside Coloyond's boundary.

## Acceptance contract used

The plan/checklist require a pooled, tokenized two-asset vault whose on-chain program checks pinned Pyth account owner/feed/freshness/confidence and price-cross/drift predicates; can stop new risk while preserving in-kind redemption without an oracle, keeper or auction; supports permissionless bounded partial fills with atomic settlement and monotonic improvement; and accounts for a holder-owned reserve plus capped, policy-limited bounty spending. Keepers may submit transactions but cannot pick executable prices, change policy, or withdraw assets. See the [rebalancing plan](../../product/onchain-portfolio-rebalancing-plan.md), especially its product loop, risk invariants and Sprint 0 gate, and [Sprint 0C in the checklist](../../product/onchain-portfolio-rebalancing-sprint-checklist.md).

“Atomic exit” means the holder's burn and in-kind transfers either all settle in one transaction or none do, including while paused and with no oracle/keeper. A multi-stage intent that eventually returns all assets is a weaker property unless an actual composed transaction is proved within Solana account/compute limits and against the deployed program.

### Pass/fail rule

Existing core may replace custom Anchor only if it **passes every** item below using source-pinned version plus an executable local/Devnet proof. “Possible by composition” is not a pass until demonstrated.

1. A permissionless public instruction evaluates the exact Pyth-backed policy, including account/feed identity, verification, age/confidence, distinct increasing `publish_time`, hysteresis and drift; no server can decide that the condition is true.
2. Holder can exit all unencumbered assets atomically while new-risk pause is active, without price/oracle, keeper, auction, or privileged actor; transfer/ATA failures roll back the whole burn.
3. Any taker can make a bounded partial fill whose token transfers and accounting are one atomic transaction; on-chain checks enforce remaining inventory, policy price/loss caps, post-fee improvement, no overshoot and single-active-intent rules.
4. Reserve is segregated from NAV/user claims, its ownership is explicit, only published bounded fees can accrue to it, and only earned/capped bounty/approved reserve actions can spend it. No administrator can sweep holder assets through a fee or authority route.
5. Roles, emergency actions, upgrades, deployed address/binary, audit scope and report-to-commit correspondence are verified and acceptable; program/account/CU limits leave margin for the actual mobile/solver transaction.

Any failure or unresolved item means **no existing custody core passes** and S1–S4 remain on the custom Anchor path. Do not create a speculative Folio wrapper or multi-protocol share wrapper as a shortcut.

## Candidate evidence

### Reserve Folio Solana: strongest alternative, but not yet proven compatible

Maintainer README describes a wholly on-chain basket with Dutch auctions. `REBALANCE_MANAGER` approves a rebalance; `AUCTION_LAUNCHER` normally opens it; a permissionless open is available only after a configured delay and when the approved initial price range permits it. The manager chooses intended mints/basket ranges and prices. The launcher has bounded latitude and privileged roles can close auctions. The documented roles are a deliberate governance trust model; they are not automatically equivalent to Coloyond's keeper-with-no-policy-authority model. See [Folio README](https://github.com/reserve-protocol/reserve-index-dtfs-solana) and [program instruction surface](https://github.com/reserve-protocol/reserve-index-dtfs-solana/blob/main/programs/folio/src/lib.rs).

The source exposes `start_rebalance`, `open_auction`, `open_auction_permissionless`, `bid`, `close_auction`, as well as separate `burn_folio_token` and `redeem_from_pending_basket`. A PDA can sign for its own address via Solana CPI, but a working controller requires a Folio role account configured to that PDA, accepted account constraints, safe instruction data, and a transaction that checks Pyth before the CPI. General CPI support does not prove those details. Source-declared IDs in `lib.rs` and `Anchor.toml` are **not** a deployment check. Anchor config has Folio IDs in localnet/devnet/mainnet sections; direct mainnet and Devnet account-owner/executable/upgrade-authority queries and exact version matching were not performed in this research package.

Reserve's README says its Folio program is non-upgradeable and describes migration to a new program with whitelist-restricted migration. That is a documented design claim; it does not establish the state/authority of any live program account. Its maintainer-published fee model includes a TVL fee and mint fee and fee-recipient distribution. No evidence found in the inspected instruction/README materials connects auction swap fees or fee recipients to a protected Coloyond holder reserve with capped bounties.

**Audit evidence:** the current Reserve Solana repository contains `audits/trail-of-bits`, `audits/cantina-spearbit`, and `audits/trust-security` directories. Trail of Bits' own public index lists “Reserve Protocol Solana DTFs” with an April 2025 report. This establishes that review artifacts exist. The PDF's exact audited commit, included programs/files, exclusions, findings, remediation/fix-review correspondence, and correspondence to the current `main` head or deployed binary were not verifiable from the materials available in this pass. Therefore this document makes **no claim that current Folio source or deployment is audited**. Sprint 0 must retrieve the reports, record scope and audited SHA, map findings to fixes/commit(s), then compare source and binary hashes for the exact candidate deployment.

### Symmetry V3

Official docs describe on-chain rebalance intents and three sequential auction windows. Rebalance eligibility includes the enabled automation flag, no active intent, bounty balance, schedule, cooldown and both absolute and relative drift thresholds. Any wallet can call keeper stage methods. Flash swap composes a vault withdrawal, a Jupiter/other DEX swap and a deposit in one transaction; the SDK's keeper is an off-chain poller and route builder, not the policy authority. Bounty funding and task claims are on-chain. This is useful comparative evidence for intent state machines and liveness incentives, but the SDK flow updates prices and makes keeper swaps across stages; it does not establish the required standalone atomic share exit or exact Coloyond conditional rule.

Sources: [rebalance lifecycle and eligibility](https://docs.symmetry.fi/concepts/rebalancing), [keeper roles and bounties](https://docs.symmetry.fi/guides/keeper), [fee/oracle config](https://docs.symmetry.fi/concepts/fees-and-oracles), [on-chain intents](https://docs.symmetry.fi/concepts/intents). The current docs were read 10 October 2026. The local probe is dated 10 October 2026 and reflects only the 40 mainnet vaults it scanned; it is not a global availability statement.

### SVS-8

SVS-8 is a multi-asset basket/share-accounting design: up to eight asset entries, configured weights and oracle accounts; authority instructions add/remove assets and update weights; users can deposit and redeem. Its documented instructions do not include an auction or autonomous rebalance transition. Its README marks Devnet availability and lists SVS-8; it also describes SVS generally as a set of SDKs/programs. Do not confuse that with independent, deployed, audited execution. The repo's current README lists an `audit/` directory but the SVS-8 spec did not provide this package enough evidence to establish a complete external audit, audited commit or deployed binary correspondence. The separate Solana Foundation vault reference has its own scope and is not evidence for SVS-8.

Sources: [SVS-8 specification](https://github.com/solanabr/solana-vault-standard/blob/main/docs/SVS-8.md), [SVS repository and status table](https://github.com/solanabr/solana-vault-standard). Its source declares an SVS-8 program ID; it is not reproduced here as a verified deployment address.

### Kamino

The current package page for `@kamino-finance/metavault-sdk` advertises instruction builders for deposits/sells, `startRebalanceIx`, `rebalanceSwapIx`, fee operations and Scope oracle integration. It lists only `0.1.0` and tests against a local validator. Its production/staging IDs are package claims, not direct chain verification. Attribution is unclear: NPM's package page identifies a non-Kamino publisher, and the official Kamino organization repository catalog identifies its lending `kvault`, lending SDK, liquidity SDK, limit-order SDK and Scope SDK, but not this MetaVault SDK. This is insufficient to call it an official, maintained Kamino product or rely on its program IDs. Do not install or use it for custody until Kamino independently confirms the package, repo, program source, deployments and audit.

Kamino's official [`kvault` README](https://github.com/Kamino-Finance/kvault) describes a **single underlying loan asset** invested into Kamino Lending reserves, not a two-asset spot basket. Its official [`kvault-bot`](https://github.com/Kamino-Finance/kvault-bot) distinguishes a permissionless `invest` crank from an allocation-rebalance loop that signs as each vault's `allocation_admin`; the bot computes and writes weights off-chain. That fails Coloyond's no-keeper-policy-authority principle and is not a candidate core. The official [`klend-sdk`](https://github.com/Kamino-Finance/klend-sdk) is a lending SDK, not proof of a MetaVault spot portfolio primitive.

## Required closure before S0F

If Folio is still considered, a separate technical probe must:

1. Pin a Folio source commit, IDL/hash, build toolchain and exact deployed mainnet/Devnet program account; query executable bit, owner, program data/upgrade state and compare binary to reproducible build.
2. Read the complete ToB/Cantina/Trust Security reports; write report dates, audited commit/files, excluded components, findings/severity, fix commits and any retest evidence. Verify correspondence rather than relying on directory names or an audit badge.
3. Build a local controller with a PDA configured as `REBALANCE_MANAGER`; in one instruction validate exact Pyth account/owner/feed/verification/freshness/confidence and distinct publish-time/hysteresis, then CPI to the approved Folio transition. Prove role constraints, no authority escalation, CPI account/compute/transaction-size margin, failure rollback and permissionless bidder behavior.
4. Demonstrate one-transaction share burn plus proportional redemption during pause with no oracle/keeper and no partial transfer on missing ATA/token failure. Measure actual accounts/CUs against the target Solana transaction format.
5. Trace every fee/reward/reserve token account and claim authority; show a bounded, immutable-per-policy fee/bounty ledger without an administrator or fee recipient sweeping backing assets. If Folio needs a wrapper-owned reserve, demonstrate it without adding a second share layer or breaking Folio NAV/redemption accounting.

No signing or live chain mutation is authorized by this research package. Until all five closure items and acceptance rules pass, the custom Anchor plan remains the selected architecture; this result does not green-light funded deployment.
