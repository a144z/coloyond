# S5 scheduler source audit

**Status:** TukTuk is the first replaceable L1 candidate. Direct Devnet reads confirm the program is executable and inspect the live config, queue census, and a bounded sample of unrelated task payloads. The project has not created a queue, registered an ETF task, confirmed any run transaction, or established public crank-turner availability. A deployed program and unrelated queues are not scheduler integration.

## Findings from official Helium sources

- TukTuk is a Solana L1 task queue/crank program. Maintainer instructions describe running a crank-turner operator; no guaranteed public Devnet executor was established.
- Queue creation documents a refundable 1 SOL minimum deposit, and each crank has a separate reward intended to cover transaction/priority fees. Queue capacity/rent and repeated task creation also have costs. A refundable minimum is not continuing automation funding.
- Queue authority and custom signer choices can expose queue funds; use a narrowly scoped queue and dedicated signer.
- Use compiled tasks only for the no-HTTP project architecture. TukTuk's `RemoteV0` obtains a signed transaction from an HTTP server and therefore requires a backend service.
- The source defines a 40-byte task-description limit and compiled instruction account indexes as `u8`. Exact ETF account list, task size/rent, transaction size, nested CPI behavior, compute units and crank reward remain to be probed; there is no single source-level limit that proves the composed ETF instruction fits.
- `TriggerV0` currently has only `Now` and `Timestamp(i64)` variants; it has no interval, cron, or account-condition trigger. A task using either variant is one-shot. TukTuk's run path can create child tasks from return data written by the exact invoked program, subject to that task's declared free-task capacity and crank-turner-supplied accounts. The ETF `poke` contract does not define or prove that return-data/requeue protocol. Therefore neither recurring calls nor a zero-maintenance condition watcher are established by choosing TukTuk alone.
- The maintained TukTuk `Anchor.toml` declares the cited program ID under `programs.localnet`, not `programs.devnet`; the separate direct account query below now confirms that the program is nevertheless deployed on Devnet. Source declarations and deployment presence still do not prove task execution.

## Devnet status

The read-only probe at [`tools/rebalancing/etf-scheduler-probe`](../../tools/rebalancing/etf-scheduler-probe/README.md) queried `https://api.devnet.solana.com`. The program account was confirmed executable under the expected loader, with space 36 and 1,001,141,440 lamports. A later account scan at confirmed slot `509634043`, block time `1791657675` (2026-10-10 18:41:15 UTC), found Devnet genesis `EtWTRABZaYq6iMfeYKouRu166VU2xqa1wcaWoxPkrZBG`, config PDA `HGBovqKte26DbEMBma3T1TvvdmAFYSSgjncRoKECqfXq`, `min_task_queue_id=2`, `next_task_queue_id=315`, and `min_deposit=1,000,000,000` lamports. The confirmed queue read was at slot `509634043` (not older than the config read); it found 312 `TaskQueueV0` accounts, 98 with task bitmap entries, 628 total occupied task IDs, 19 with zero queue-authority count, and configured crank rewards from 0 to 1,000,000,000 lamports. These are live account facts, not a public-executor or liveness claim. Queue-account lamports include rent-exempt allocation and are not reported as spendable funding. The `hpl-crons` queue was one example with occupied task IDs; no task payload or execution transaction was inspected. No scheduler transaction has been sent.

The read-only probe now makes a bounded sample of up to 15 live `TaskV0` reads from up to five queues and three occupied IDs per queue. It decodes the maintained Borsh fields, labels `CompiledV0` versus `RemoteV0` and `Now` versus timestamp triggers, validates compiled account indexes and signer-seed limits, checks task queue/ID against the sampled queue bitmap/capacity, derives each sampled task PDA from `[b"task", task_queue, task_id.to_le_bytes()]`, and fails when the RPC account key differs; it reports transaction payload bytes, rent field, crank reward and account lamports separately. Remote URLs and signer keys are omitted from output. Eight parser tests cover both source variants and trigger forms, index/seed failures, unknown variants, truncation, UTF-8/description and zero-padding behavior, bounded ID sampling, config fields, queue occupancy and base58 leading zeros. Seven offline size tests cover Borsh lengths, account-index bounds, PDA seed count/length, and the returned-task growth limit. Three PDA tests compare six standard-library derivations with `solana-pubkey` 2.4.0 vectors, validate the `u16` task-ID boundary and reject malformed queue keys. The returned-task model adds a strict direct `RunTaskReturnV0` Borsh parser and deterministic child-task checks for capacity, IDs, rewards, descriptions, compiled indexes, per-signer limits of 16 seeds/32 bytes each and the supported compiled-only policy; its 25 tests are offline fixtures, including maximum signer-seed boundaries, invalid free/occupied task-ID rejection including duplicate occupancy, task-queue address validation even for zero-child returns, supplied task-account PDA/order/emptiness checks, and compiled-message header account-class consistency. The combined probe suite now has 43 passing tests. These models do not establish queue/task rent or reward funding, actual account ownership/PDA availability, transaction sizing, invocation, recurrence, or external crank-turner availability. No task was submitted or executed.

## Bounded live TaskV0 sample — 10 October 2026

The extended probe ran read-only against Devnet at queue-census slot `509646765`, block time `1791660732` (2026-10-10 19:32:12 UTC), on the expected genesis. It observed 312 queues and 632 occupied task IDs. The bounded sample selected five active queues and up to three bitmap IDs per queue; one task lookup in queue `crank-tester8` changed/disappeared between queue and task reads and was reported as a snapshot race rather than treated as a decode failure. Ten task accounts decoded successfully: three unrelated tasks were `RemoteV0`, seven were `CompiledV0`, and all sampled triggers were `Now`. The compiled task payloads ranged from 197 to 487 serialized bytes; remote task payloads occupied 137 or 197 bytes. Account lamports include rent/reward effects and are not evidence of queue spendable funds. No ETF payload was examined, no task was submitted, and no run transaction or external crank-turner was verified.

## Independent task-PDA verification — 11 October 2026

The read-only probe was refreshed at the same Devnet genesis. Its queue census was at confirmed slot `509660245` and observed 312 queues with 653 occupied task IDs. The bounded sample selected five queues: ten `TaskV0` accounts decoded successfully (seven `CompiledV0`, three `RemoteV0`), while one task disappeared between queue and task reads. For each successful account, the probe derived the expected PDA from TukTuk's [maintained queue instruction](https://github.com/helium/tuktuk/blob/main/solana-programs/programs/tuktuk/src/instructions/queue_task_v0.rs) seeds `[b"task", task_queue, id.to_le_bytes()]` and matched the RPC account address. The same standard-library derivation matches six offline vectors generated with `solana-pubkey` 2.4.0. This verifies only sampled TaskV0 address derivation and account identity; it does not prove ETF payload compatibility or execution. No queue/task was created, and no transaction or crank-turner was observed.

## Trigger and recurring-execution source audit — 11 October 2026

The maintained [`TriggerV0` enum](https://github.com/helium/tuktuk/blob/main/solana-programs/programs/tuktuk/src/state.rs) contains `Now` and `Timestamp(i64)` only; `Timestamp` becomes active once the current time reaches its timestamp. Neither variant repeats itself, and there is no state/account-change trigger in this enum. The maintained [`run_task_v0` implementation](https://github.com/helium/tuktuk/blob/main/solana-programs/programs/tuktuk/src/instructions/run_task_v0.rs) supports creating follow-up tasks from return data owned by the invoked program, and the current task declares `free_tasks` capacity. This is a possible source-level mechanism for recurring execution, not a proven ETF design: ETF `poke` would need a reviewed, bounded child-task protocol, exact returned payload and accounts, capacity/rent funding, stop/cancel behavior, and a distinct crank-turner that keeps submitting runs. The source also requires free task IDs and matching empty task PDAs, returned child rewards of `None` or the exact queue minimum, and per-task growth within Solana's 10,240-byte limit. The offline models now cover the direct return wire shape, a subset of deterministic child constraints and the account-growth formula, but they do not verify live ownership, PDA availability, rent/reward funding, queue solvency, stop policy or execution. A timestamp task can request one future execution but cannot itself express an unbounded interval. Until an ETF program and external crank-turner pass the real invocation proof, TukTuk remains a one-shot candidate and the blueprint's recurring, condition-triggered, zero-maintenance claim remains unresolved.

### Direct returned-task wire and constraint model — 11 October 2026

The maintained [`RunTaskReturnV0` source](https://github.com/helium/tuktuk/blob/main/solana-programs/programs/tuktuk/src/instructions/run_task_v0.rs) defines direct return bytes as Borsh containing a vector of `TaskReturnV0` values followed by a vector of task-list account keys. Each returned task includes a one-shot trigger, compiled or remote transaction source, optional crank reward, `free_tasks` count and description. TukTuk reads the direct result strictly with `try_from_slice`, so malformed bytes and trailing bytes fail the run. It applies the 1,000-byte direct-return bound and offers an owned task-list account path for larger data. Returned tasks are constrained by the parent task's declared free-task capacity, caller-supplied unused IDs and matching empty task PDAs, queue capacity, the 40-byte description limit, a reward of `None` or exactly the queue minimum, per-task 10,240-byte growth, and available task/queue funds.

The new [`returned_tasks.py`](../../tools/rebalancing/etf-scheduler-probe/returned_tasks.py) parser checks only the direct Borsh structure and a subset of deterministic policy checks that can be evaluated from explicit fixture context. Its child validator now applies the same per-signer limit of 16 PDA seeds and 32 bytes per seed as the live-task decoder and offline size model, including independent validation of multiple signer groups. It parses `RemoteV0` but rejects it for the no-backend candidate, and it refuses the alternate `tasks_accounts` path rather than silently treating it as covered. It does not verify return-data program ownership, account keys/owners, live queue bitmap state, rent or reward funding, free-task PDA existence, executor behavior, or repeated execution. Its passing tests are source-shaped offline vectors, not evidence that an ETF program returns usable tasks or that TukTuk invokes them.

The separate offline [`payload_size.py`](../../tools/rebalancing/etf-scheduler-probe/payload_size.py) models Borsh `TaskV0` account data from parameterized compiled instruction shapes. It includes account-key vectors, instruction account/data vectors, signer-seed vectors, the one-shot trigger, description, enum tags and Anchor discriminator; it checks the referenced `u8` indices, the parser-matched maximum of 16 seeds per signer and 32 bytes per seed, and reports serialized account-data bytes. A sample one-key `Now` task with one one-account/two-byte instruction encodes to 168 serialized bytes. Five local size tests pass alongside the eight existing account-probe tests.

This serialized length is not the space TukTuk's queue instruction reserves. The maintained [`queue_task_v0`](https://github.com/helium/tuktuk/blob/main/solana-programs/programs/tuktuk/src/instructions/queue_task_v0.rs) allocates `8 + size_of::<TaskV0>() + transaction.size() + 4 + description.len() + 60`. Its [`CompiledTransactionV0::size()`](https://github.com/helium/tuktuk/blob/main/solana-programs/programs/tuktuk/src/state.rs) is a custom heuristic based on the transaction header, maximum referenced account index and compiled instructions; it does not include serialized signer-seed vectors. The host- and target-layout-dependent `size_of::<TaskV0>()` also is not the Borsh body length. Consequently the 168-byte sample must not be used to predict account allocation, rent or successful task creation. Exact allocation/serialization fit remains an S5D1 proof obligation once the ETF account list and target payload are frozen. Neither measurement predicts full transaction packet size, compute units, CPI feasibility, or crank-turner behavior; no actual ETF payload is sized.

## Required proof before S5/CP5 can pass

1. [x] Read Devnet genesis and prove the exact TukTuk program account exists, is executable, and has the expected loader owner (one point-in-time read; refresh before any task creation).
2. Wallet-sign queue creation/funding; record the 1 SOL deposit separately from queue/task rent and per-crank reward.
3. Register a compiled task with the exact public ETF `poke` instruction; record registration signature, queue/task PDAs, task ID, trigger and decoded payload, then read back the task account independently.
4. Capture a separate confirmed task-run transaction signed by the identified external crank-turner. Its inner instruction must invoke exactly `poke` and its before/after pool state must show eligibility/maintenance only.
5. If recurring behavior is required, first freeze a protocol-native one-shot/requeue contract, then prove every returned task, account, rent/reward funding, stop condition and successive external crank transaction. A single `Now`/`Timestamp` task is not recurring evidence.
6. Separately prove a trader wallet supplies SPL input for `swap_exact_in`. The scheduler invocation must not be described as a trade.
7. Prove permissionless direct `poke`, swaps and in-kind exits still work if the scheduler is unavailable.

If TukTuk fails the direct Devnet checks, evaluate another demonstrated L1 scheduler against the same `poke` contract. MagicBlock Ephemeral Rollups change the execution environment and are not a drop-in L1 replacement. If no candidate passes, Sprint 5 and CP5 stay blocked; a local simulation is not a substitute.
