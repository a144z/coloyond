# ETF AMM v1 read model

**Status:** S5A draft. Read-only projection over the ETF program and exact Devnet manifest; it is not a source of protocol authority. Unknown, stale, or unavailable data is represented as unknown, never as zero.

| View | Source of truth | Required fields |
|---|---|---|
| Network and deployment | Solana RPC plus deployment manifest | Cluster, genesis hash, RPC endpoint label, commitment, program ID, executable/loader check, pool address, config hash/revision, observed slot and fetch time. |
| Pool configuration | `EtfPool`, ordered `EtfAsset` accounts and the manifest whose canonical bytes match the on-chain hash | Canonical config bytes/hash and `etf1:<config-hash>` strategy ID, protocol/math version, fee/risk policy IDs and parameters, immutable initial governance/guardian identity commitment, current governance/guardian roles, persisted `Unseeded`/`Active`/`Closed` lifecycle, pause state, target weights, asset order, mint, token program, decimals, custody address, share mint, initializer/rent payer, delay and pending governance proposals. Reject a missing or mismatched manifest; it cannot override on-chain bytes. |
| Asset balances | Each PDA custody token account | Raw base units and decimals per asset, RPC context slot, account owner/mint checks. Mints must be unique within each snapshot. A missing or mismatched account is an error state. |
| Oracle observations | Exact stable feed account pinned in the canonical config and manifest-declared mode | Account key/owner, feed ID, raw price/confidence/exponent, publish time, age at chain observation, RPC context slot, and validation result. ETF v1 pins a stable key for either mode. Both modes use the Receiver `PriceUpdateV2` layout and require `Full`; `PushFeed` additionally proves fixed PDA derivation and sponsored update status. Per-transaction ephemeral update accounts are outside this v1 identity schema. |
| Portfolio value | Checked client projection using on-chain observed balances and accepted oracle observations | Estimated NAV, per-asset oracle-marked value, actual value weights, target value weights, deviation, source slots and valuation time. Label as estimate, not executable price or redeem value. |
| Shares | Classic SPL share mint and user token accounts | Mint decimals, total supply, connected wallet share balance, last confirmed mint/burn signature and slot. |
| Swap preview | Deterministic ETF v1 math output plus current account snapshots | Direction, gross input, fee, estimated output, min-out, expected post-swap deviation, oracle bounds, account slots and expiry. A preview is not a fill guarantee. |
| Fee observation | `EtfAsset` cumulative fee base-unit counter plus `SwapExecuted` events | Counter by asset, latest per-swap fee event/signature, custody balance. The fee count is informational and does not create a liability or separate asset balance. |
| Scheduler | TukTuk program/queue/task reads, when a scheduler is admitted | Candidate status, program executable/loader proof, queue authority, balance, capacity/rent, task PDA/ID, exact compiled payload, trigger, crank reward, last crank transaction and crank signer. Unknown executor availability is shown as unverified. |
| Wallet action | Durable client pending record plus signature/confirmed RPC transaction | Intent, serialized message hash, signer, submitted/confirmed/rejected/unknown state, endpoint genesis, signature, confirmation slot, actual token deltas. Unknown never invites an automatic resend. |

All projections keep **target weight**, **actual value weight**, **NAV estimate**, **share-token balance**, **AMM quote**, and **confirmed transaction result** as separate facts. The UI must show full mint/feed identifiers and explicit synthetic/unbacked labels for Devnet test mints. A ticker or image does not select an asset. No UI may infer a successful scheduler run from a cron timestamp or a task registration signature.

## Provisional client boundary candidate

S5A has not accepted or frozen this behavior-level port. It is a design candidate to guide fixture review; until the remaining required fields and account bindings are resolved, S5F is limited to fixture validation and S5G to synthetic presentation. Neither package may treat this text as authority to build production RPC or transaction behavior:

- **Read:** load a pool snapshot and wallet balances with network genesis, RPC context slot, source freshness and explicit unknown/error states.
- **Preview:** quote a seed, proportional deposit, in-kind redemption, swap or `poke` using a specific snapshot and return the account identities, limits, expiry and oracle evidence needed for wallet review.
- **Build:** produce an unsigned, reviewable transaction message tied to that same snapshot and manifest. It does not submit or sign.
- **Reconcile:** accept the wallet signature and report `submitted`, `confirmed`, `rejected` or `unknown` only after querying the pinned cluster and comparing confirmed token/share deltas.

Before any seed/deposit action, each client must recompute the approved manifest's config hash, strategy ID and PDA seeds; compare the fetched immutable identity and initial-authority commitment; and verify current governance/guardian state against the accepted manifest or a valid delayed handoff. Matching only a pool address or hash is insufficient. A valid handoff updates current roles but never rewrites initial authority fields or pool identity. After S5A review, the TypeScript client and Android Kotlin adapter may implement the accepted port independently from the same read-model and IDL vectors. The Android UI can develop against a contract-conforming fake port for presentation work, but S5H must replace it with the real adapter; fake-port activity never counts as a wallet, RPC or transaction proof.

### Proposed cross-language DTO and fixture semantics

The semantics below are proposed for S5A review. They are not yet a frozen schema, and current fixtures exercise only a subset of the complete snapshot/action model. `configRevision` is the required immutable lowercase config-hash hex string; `protocolRevision` is the required `etf-v1` protocol label. Neither changes on seed, trade, pause or authority handoff. `poolSequence` is the required decimal-string copy of `EtfPool.sequence`, the mutable state revision, which increments on every committed pool-state transition; reads and previews bind it. `protocolRevision` cannot be null or fall back to the config hash. Before S5F production work, S5A must add and validate complete deployment, pool configuration, custody identity, portfolio, share, oracle-source and wallet-action fields against the requirements above. Both clients must preserve these meanings after acceptance; language-specific wrappers are allowed, but neither may weaken validation or convert an unknown value into zero.

- Addresses, hashes, signatures and feed IDs are base58/hex strings exactly as returned by the pinned protocol/manifest.
- Every unsigned or signed integer that can exceed JavaScript's exact integer range (`u64`, `i64`, token amounts, slots, sequence numbers, lamports, raw prices and confidence) is a base-10 string. Bounded enum values and small exponents may be JSON numbers only where the contract gives an explicit range.
- A Pyth exponent is a signed `i32` JSON number at the wire boundary; the separately reviewed oracle/math policy decides which exponents are accepted for valuation. Keeping the wire type does not approve a production exponent limit.
- Observation state is a tagged union: `available` carries a value and source context; `stale`, `unavailable`, `invalid` and `not_configured` carry a stable reason code and never a numeric placeholder. A failed snapshot (`kind: observation`) may include only non-value metadata plus an omitted or null `value`; it must not carry available `oracle`, `balances` or `pool` payloads. A failed oracle-only observation may retain diagnostic fields such as feed identity and age alongside its reason.
- An optional oracle field may be omitted when no oracle payload is present; an explicit `null` is malformed. `protocolRevision` and `configRevision` are required nonempty strings with the meanings defined above; no nullish aliasing is permitted.
- Oracle observations use the shared `PriceUpdateV2` verification semantics for both modes and must show `Full`. The mode tag distinguishes fixed `PushFeed` from stable Receiver-owned `ReceiverFull`; both account keys are pinned in the immutable pool config. Per-transaction ephemeral account keys require a future schema change and are not admitted by ETF v1.
- A wallet action is one of `draft`, `awaiting_signature`, `submitted`, `confirmed`, `rejected` or `unknown`. Only `confirmed` contains a confirmation slot and RPC-derived token/share deltas. `unknown` preserves the signature/message identity if known and cannot trigger an automatic resend.
- Every read and preview includes cluster genesis, RPC context slot, protocol revision, immutable config revision and mutable pool sequence. A preview additionally binds expiry, exact account keys, limits and oracle evidence; a transaction builder must consume that same snapshot identity.

S5A owns `docs/rebalancing/contracts/etf-read-model-v1-fixtures.json`. The current corpus contains component-level examples for available, stale, unavailable, both oracle modes, integer precision and confirmed/unknown receipts; it is not a complete snapshot contract or a conformance source for production S5F/S5G. The Python and TypeScript fixture validators enforce the same fixture-local invariants and required corpus examples, including that only confirmed receipts carry RPC-derived effects. The document remains `fixtureOnly`; validator success does not freeze any open production contract, risk, fee, authority or deployment choice. Do not add an extra schema/code-generation dependency for this contract.
