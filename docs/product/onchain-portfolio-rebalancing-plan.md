## 1. Decision in one page

Build two explicitly versioned Coloyond protocol paths. The current **v0.3.0 two-asset Anchor vault** keeps its proportional share accounting, policy checks, and permissionless Dutch-auction settlement. A separate **v1 multi-token ETF AMM** becomes a major foundation pillar in Sprint 5, with its own program identity, accounts, IDL, share accounting, math/oracle modules, SDK and deployment manifest. The v1 AMM is not a rewrite of v0.3.0: neither program inherits the other's settlement assumptions, and neither account layout or strategy identity is reinterpreted. Core custody, accounting, pricing constraints and swaps live in Solana programs; wallet UI, RPC reads, transaction construction, monitoring and transaction submitters remain off-chain. Solana programs run only when a transaction invokes them. Keepers and scheduler crank-turners can improve liveness, but cannot cause autonomous execution or supply a missing trade counterparty. [Solana execution model](https://solana.com/docs/core/programs/program-execution), [Solana transaction model](https://solana.com/docs/core).

Use the exact official Pyth account mode and SDK for each protocol; fixed sponsored price-feed PDAs and ephemeral `PriceUpdateV2` updates have different derivation, lifetime and update flows, but current Solana integration uses the same Receiver `PriceUpdateV2` layout and Pull Oracle account owner for both. The existing v0.3.0 path already parses its source-listed fixed-feed candidates with this type. S5C directly confirms the candidates on Devnet and independently reproduces their shard-zero addresses; S0B remains held for its remaining deployment/admission conditions, not an owner/parser mismatch. ETF v1 continues to prefer fixed sponsored accounts; ephemeral updates remain a reviewed alternative if freshness/update requirements justify their wallet flow. Feed publication and RPC availability depend on external infrastructure; no heartbeat is a guaranteed update schedule. Use the existing [Solana Mobile Wallet Adapter Kotlin client](https://docs.solanamobile.com/android-native/using_mobile_wallet_adapter) for user signatures. The v0.3.0 settlement remains a permissionless Dutch auction between the vault and external takers. The new ETF settlement is a bounded weighted-mean AMM swap: independent traders can arbitrage toward the pool's configured value weights, but the program never invents an opposite-side trade. Its scheduler adapter is replaceable and can only invoke explicitly bounded on-chain maintenance/eligibility instructions. Helium Cron plus TukTuk is the first recurring L1 scheduler candidate to prove on Devnet; it still depends on Cron/queue funding and external crank-turner submission. MagicBlock's Ephemeral Rollup path is not the selected strict-L1 execution model, and Antegen's current deployment/executor evidence is insufficient. No option supports the blueprint's literal “zero off-chain infrastructure” claim. Solvers may use on-chain venues; Jupiter Swap V2 Router `/build` is optional route construction only after account, CPI, and Devnet behavior pass an integration probe. ## 2. Product contract and trust boundary

**Product choice:** a pooled, tokenized vault per *published* strategy, starting with one curated WSOL/USDC strategy. A card remains an immutable expression of a strategy configuration revision. A saved target does not silently move assets; the user explicitly selects a live vault and signs a deposit. A remix may produce a draft, and a new on-chain vault is not implied until its configuration is published. This matches the repo's existing strategy/card model and avoids one program deployment per user. Permissionless vault creation is a later factory milestone, after one vault's economics and attack surface are measured.

| On-chain and enforceable | Off-chain, replaceable and never a source of authority |
|---|---|
| Asset and share balances; target weights; policy revision; trigger predicates; price-account ownership/feed/freshness checks; auction curve and bounds; fill accounting; fee/bounty ledger; expiry and cancellation | Wallet UI, card art, RPC/indexer, alerting, keeper scheduling, solver route discovery, transaction assembly and submission |
| The vault program moves assets only under its published rules | A keeper can suggest a transition and pay a transaction fee; it cannot set a favorable price, bypass caps, or withdraw assets |

Oracle publishers and RPC operators are external dependencies even when price proofs and results are consumed on-chain. “Fully on-chain” does **not** imply guaranteed execution, exact continuous weights, no MEV, or profit. If no one submits a transaction or fills a bounded auction, the vault stays at its last on-chain state and users see a stalled status. The program keeps in-kind redemption callable under emergency pause; a frozen underlying token account or unavailable chain can still prevent actual transfer. [Solana token freeze semantics](https://solana.com/docs/tokens/basics/freeze-account).

### End-to-end user and protocol loop

1. **Publish policy:** governance sets asset mint/feed allowlist, target weights summing to 10,000 bps, drift thresholds, max trade and loss budgets, cooldown, fee bounds and timelock. A configuration hash/revision links the vault to the card.
2. **Enter:** wallet signs a proportional basket deposit. The program transfers underlying tokens to PDA-controlled token accounts and mints SPL shares with `minSharesOut`. WSOL is the canonical SOL asset; client wrapping is explicit. The initial seed requires fresh oracle valuation, a minimum locked share amount, an approved target ratio and a disclosed seed contribution to the holder-owned automation reserve; otherwise the first rebalance cannot pass its bounty-funding guard. Subsequent proportional deposits use current backing ratios, so they do not require a spot quote or transfer value from existing holders.
3. **Observe:** anyone reads the same pinned Pyth on-chain feed accounts and invokes `observe_condition` or `start_rebalance`; a price pusher may update those feeds independently when necessary. The program checks fully verified price, feed, age and confidence, then computes value weights in integer/fixed-point math. When a rule or drift condition is satisfied, it records a deterministic, single active rebalance intent.
4. **Trigger:** after cooldown and policy checks, anyone invokes `start_rebalance`. The program freezes a bounded auction plan for overweight-to-underweight assets. A conditional price rule may first change targets by a preauthorized amount, then open the same rebalance path.
5. **Fill:** any taker supplies the deficit asset and receives the surplus asset in one Solana transaction. The program verifies fresh price, auction price, size, slippage/value loss ceiling, direction, remaining inventory and monotonic improvement toward the target before transfers. Partial fills are allowed. A solver may atomically fund its leg from a DEX, but the vault is safe even if that route fails.
6. **Settle:** explicit fill fees stay in vault-controlled accounts; an on-chain rule assigns a bounded portion to automation reserve. Claimable keeper bounties accrue only after verified useful transitions. When the target band is reached or the auction expires, anyone finalizes. State, fees, actual weights, timestamps and signatures can be independently read from Solana.
7. **Exit/recover:** a holder burns shares for a proportional, in-kind claim on all unencumbered backing, including their share of unused reserve. The program-level path needs no oracle, keeper, Jupiter share-token route, or live auction. Pending liabilities are accounted for before redemption. Emergency pause blocks new risk while preserving this path; an issuer freeze or chain outage remains an external transfer risk.

**v0.3.0 first published vault assets:** provisionally classic SPL WSOL and USDC, conditional on mint-authority, freeze-authority, liquidity and oracle review. The older spec never mandates USDC or an issuer-free stablecoin: its illustrated assets are examples, its allocation drafts may express desired mints, and only an exact match to a verified published vault can become financial. Therefore use the old spec's full-mint, allowlist, configuration, independent entry/exit and disclosure discipline for technical asset admission; no new user policy decision about USDC is needed now. USDC carries issuer/freeze risk even though portfolio execution is on-chain; disclose and test that external-transfer limit, and never suggest the program can redeem a frozen token account. If WSOL/USDC fails a technical admission check, leave that vault unavailable and re-evaluate its asset set under a new manifest. Token-2022 extensions, unverified mints, lending, leverage, LP ranges, cross-chain routes and one-click single-token deposits add different risk models and are outside this first vault. Source mint addresses, token program IDs and full Pyth feed-account addresses/IDs must be frozen in a reviewed deployment manifest, never inferred from symbol text. [Solana token-program distinction](https://solana.com/docs/payments/how-payments-work), [Pyth feed/account validation](https://docs.pyth.network/price-feeds/core/use-real-time-data/pull-integration/solana).

**Separate v1 ETF AMM asset set:** Sprint 5 will prove a bounded three-asset Devnet pool shaped by the colleague's SOL/BTC/USDC example. Each entry is a specific SPL mint and specific Pyth feed, never a ticker. No admitted or backed BTC Devnet token is established in current repo evidence; if a synthetic test mint is used with a BTC/USD feed, every screen, manifest and checkpoint must label it as an unbacked test token. Sprint 5A must verify all mint authorities/decimals/token programs, feed IDs/accounts/owners/verification/freshness, and actual Devnet transaction feasibility before the configuration is frozen. A failed asset gate reduces the test set or blocks the pool; it does not permit symbol-based substitution. This single multi-asset pool is distinct from Sprint 8's catalog of multiple independently published pools.

## 4. On-chain contract design

**v0.3.0 auction accounts, all versioned and PDA-derived:** `Vault` (asset mints, target bps, revision, share mint, governance and pause flags); one `AssetPosition` and custody token account per asset; `OraclePolicy` (pinned canonical feed-account addresses and feed IDs, owner, max age/confidence/deviation); `ConditionalRule` (price-cross/schedule predicate, prior observed price and strictly increasing publish time, hysteresis, expiry, target revision and nonce); one active `RebalanceIntent` per vault; `Auction` (pair, snapshot, bounded price curve, start/end, remaining size); `AutomationReserve` per asset plus explicit unpaid bounty liabilities; and `GovernanceProposal` with timelock. These describe the current auction protocol only. ETF v1 has a separate account model below. Separate event versions permit deterministic index reconstruction; unknown versions fail closed.

**v0.3.0 instructions:** `initialize_vault`, `propose_policy`, `execute_policy_after_timelock`, `deposit_proportional`, `redeem_in_kind`, `observe_condition`, `activate_condition`, `start_rebalance`, `fill_auction`, `finish_or_expire`, `claim_bounty`, `pause_risk`, `resume_risk`, and `sync_donation` under a published rule. Each writes a sequence number so repeated keeper submissions are idempotent or reject on stale state. No manager can transfer underlying tokens to an arbitrary wallet. High-risk **configuration** changes use the program's on-chain multisig/timelock policy; emergency pause is narrower than governance. The Solana loader's separate `ProgramData` upgrade authority can bypass in-program rules, so it must be transferred to an independently enforced on-chain multisig plus delay mechanism, or revoked after the upgrade policy is settled. Its actual address and delay are launch-gate evidence. [Solana program upgrades](https://solana.com/docs/core/programs/program-deployment).

**v0.3.0 share invariant:** total issued shares represent a pro-rata claim on **all** unencumbered portfolio and reserve assets. Pending bounty liabilities are excluded. The current bootstrap requires a pre-created zero-supply share mint and empty PDA-controlled custody accounts; it atomically creates Vault/Governance state, transfers the first seed and mints shares, so a pre-seed donation cannot be mistaken for the seeder's deposit. Fresh fully verified prices define seed NAV at the Pyth lower confidence bound (`price - confidence`). Current source uses a provisional $1/share unit at six decimals with floor rounding and a minimum locked supply floor; this is a conservative implementation convention, not an approved market price or finalized economic term. Bootstrap oracle limits are signed by the current program upgrade authority and must match the reviewed deployment manifest; they are not yet approved or transaction-validated. The bootstrap, authority rejection and seed rollback have synthetic-fixture Localnet transaction evidence; this does not prove Pyth authenticity, Devnet admission, or Android wallet behavior. Later deposits mint from the minimum per-asset backing ratio using vault-favoring rounding; unused inputs return in the same transaction. Redemptions burn before transferring the caller's pro-rata asset and unused-reserve portions, with explicit dust rules. Auctions do not escrow extra inventory: each fill is bounded by current custody balances and the current surplus. Proportional redemption during an auction reduces those live limits, while the frozen auction's remaining cap remains an upper bound; exit never waits for bidders. A direct token donation after initialization cannot silently change accounting: `sync_donation` credits it to holder backing under deterministic rounding, and deposits/redemptions either sync first in the same transaction or reject until synced. No float arithmetic, unchecked decimal conversion, or share calculation from target weights alone. `minSharesOut` and `minAmountsOut[]` protect the user.

**v0.3.0 trigger math:** normalize token-base amounts, mint decimals, Pyth price/exponent and confidence under checked fixed-point arithmetic. The v0.3.0 source deserializes the manifest's fixed shard-zero feed PDAs as Receiver `PriceUpdateV2`. S5C's direct Devnet reads and official Pyth SDK derivation test confirm the expected account owner, layout, feed ID and address derivation; these do not by themselves satisfy S0B's deployment/admission gates or prove an on-chain consumer transaction. For both fixed feeds and ephemeral updates, require Pull Oracle ownership, exact account/feed identity, `Full` verification, positive nonfuture price, maximum age, confidence and supported precision. The client distinguishes the fixed `[shard, feed ID]` PDA from an ephemeral account posted with the transaction. A rebalance may start only if policy is enabled, no rebalance is active, the reserve can fund the bounded bounty, schedule is open, cooldown elapsed, and at least one asset exceeds configured drift. Use separate start and stop bands; their numeric values require economic review. A price-cross rule needs strictly increasing Pyth `publish_time`, separation, hysteresis, nonce and expiry checks. A stale, missing, partially verified or wide-confidence source blocks new risk. A different Pyth account mode requires an explicit compatibility-tested manifest amendment. [Pyth fixed feed and update account modes](https://docs.pyth.network/price-feeds/core/use-real-time-data/pull-integration/solana), [Pyth contract addresses](https://docs.pyth.network/price-feeds/core/contract-addresses/solana), [Pyth price safety](https://docs.pyth.network/price-feeds/core/best-practices).

**Auction safety:** the program snapshots eligible overweight-to-underweight pairs but checks a current price on every fill. The publicly computable Dutch price moves within a governance-set oracle-relative band over a fixed window. For every partial fill, verify both token-account deltas and that the **post-fee, post-bounty** deviation measure falls by at least a dust-adjusted minimum; cap per-fill and per-epoch size, prohibit overshoot, and limit conservative oracle-marked NAV loss including fees and bounties. Fees are taken from the incoming asset in the same fill and credited to vault-controlled ledgers. Oracle latency and adverse selection still exist at a fresh timestamp, so the band must include confidence, size and cumulative-loss limits. Expiry cannot extend its own price band; re-evaluation requires a new intent. A solver may compose a route before/after `fill_auction`, but the vault never approves a generic arbitrary program or token account. The Solana transaction is atomic for each fill, not across an entire multi-fill rebalance. [Solana atomic transactions](https://solana.com/docs/core), [Folio auction reference](https://github.com/reserve-protocol/reserve-index-dtfs-solana), [Pyth executable-price risks](https://docs.pyth.network/price-feeds/core/best-practices).

**Fee and bounty economics:** do not copy YieldBasis percentages or assume Jupiter fees return to this vault. Only fees explicitly charged by `fill_auction` are protocol revenue; a disclosed seed contribution bootstraps the holder-owned reserve before any fees exist. A versioned on-chain split credits (a) unrestricted holder backing and (b) that reserve, both included in NAV; any unused reserve is part of in-kind exits. The reserve can pay only an earned, capped keeper bounty after an observed useful transition, with per-epoch spend and minimum-balance floors. Model `net benefit = fee + price improvement − adverse selection − bounty − transaction/solvency cost`. Sprint 4 must compare candidate fee/split levels under quiet, trending and volatile markets before fixing mainnet values. An auction can be uneconomic or unfilled; the reserve is not an invented yield source.

It must not add AMM semantics to `programs/coloyond-vault` v0.3.0 or reinterpret v0.3.0 `cb3:` identities. The old Sprint 0 identity freeze applies to v0.3.0 `cb3:` only; ETF v1 receives a new, separately versioned strategy identity frozen in S5A.

**Pool and custody modules:** begin with a fixed maximum of three admitted SPL assets per pool. `EtfPool` stores immutable pool identity, bounded target weights summing to 10,000 bps, configuration revision, share mint, fee policy, pause state and sequence. The configured target weights are the normalized exponents in the weighted invariant; oracle-marked actual value weights use decimal-normalized token balances multiplied by each exact feed price, and the rebalance eligibility check compares those value weights to the configured target. Each asset has an `EtfAsset` record binding the full mint, token program, decimals, PDA custody account, and exact oracle feed key/ID. Pool creation is permissionless at the canonical config-derived PDA; any signer may pay rent, while the initial authorities and economics are committed by the config bytes and pool identity. The client verifies the approved manifest before exposing seed/deposit actions. Asset/feed/target/fee configuration is immutable for that pool identity, and a change requires a new pool identity. A narrow emergency guardian may pause risk-increasing actions but cannot transfer assets or block in-kind withdrawal; unpause is a delayed governance action. Keep account validation, custody transfers, share accounting, oracle verification, weighted math, swap/fee policy, scheduler integration, and clients in separate modules/packages. The first v1 implementation does not use Token-2022, lending, leverage, LP positions, cross-chain routes or arbitrary CPI programs. Deposits and redemptions are proportional and explicitly previewed; no pause or administrator can disable a valid in-kind exit.

**Weighted invariant and swaps:** model the pool on a weighted constant-mean invariant `k = ∏ reserve_i^(weight_i)`, with normalized weights and token decimals/exponents applied before value comparisons. Port or derive fixed-point math in an isolated pure Rust module; bound inputs, asset count, exponent, rounding error and compute units. S5B must derive the relationship between quantity-reserve invariant exponents and USD-denominated target weights using oracle prices and mint decimals; it must prove that useful trades can satisfy both weighted-invariant preservation and the separate custody/share-backing bounds, as well as the post-fee portfolio-deviation improvement rule. Do not use “solvency” as a synonym for invariant preservation: the invariant is not dollar NAV, share backing, or a profit guarantee. If these constraints conflict, amend the quote model before S5E instead of silently weakening a guard. Reject overflow, underflow, unsupported decimals and quotes outside configured bounds. A swap instruction must atomically transfer input and output SPL tokens, apply `min_amount_out`, per-trade inventory limits, oracle-relative price bounds and a post-fee invariant check. Golden vectors must compare quote and invariant behavior against an independently coded high-precision reference across all supported weights/decimals and adversarial boundaries. Fees can increase the invariant while LPs still lose value to adverse selection, depeg or market moves.

**Oracle and fee guard:** use Pyth Core feeds through the exact account mode and parser proven by S5C. Pyth documents two Solana paths: fixed sponsored shard-0 price-feed accounts under its Push Oracle program, and ephemeral `PriceUpdateV2` accounts owned by its Receiver/Pull Oracle program. Their addresses, lifecycle and update paths differ. The official Push Oracle implementation CPI-calls Receiver `post_update` for the fixed PDA and deserializes it as `PriceUpdateV2`; the official TypeScript SDK derives the fixed PDA under Push Oracle and fetches it through the Receiver `priceUpdateV2` coder. The pinned Rust adapter now confirms the candidate account owner, layout, feed ID, actual `Full` verification and PDA derivation. The ETF's first candidate remains fixed sponsored feeds because this update path avoids posting a Pyth update in each user transaction. Freeze confidence/exponent limits and stale-feed recovery before S5E. Both fixed feeds and ephemeral updates require `verification_level == Full`; fixed mode additionally pins the derived PDA and relies on the sponsored/permissionless updater path. Partial verification is not an automatic fallback. In either path validate positive price, maximum age, confidence ratio, exponent and checked fixed-point conversion. Pyth's Devnet sponsored-feed table lists shard-0 SOL/USD, BTC/USD and USDC/USD candidates with a nominal 55-second heartbeat and 0.5% deviation; that is not a freshness SLA. See the [Pyth Solana integration guide](https://docs.pyth.network/price-feeds/core/use-real-time-data/pull-integration/solana), [Devnet program addresses](https://docs.pyth.network/price-feeds/core/contract-addresses/solana) and [sponsored feed list](https://docs.pyth.network/price-feeds/core/push-feeds/solana). Pin the supported feed set in the ETF v1 manifest and refresh each account on Devnet before admission. Finalized Mainnet/Devnet captures now confirm point-in-time identity and parser compatibility for all three candidates; three Mainnet baskets passed only a diagnostic 60-second age check (10/42/33 seconds), while three Devnet baskets failed it (140/310/166 seconds; latest 166). This does not establish continuing availability or admission. The existing v0.3.0 source has a SOL/USDC asset profile; it does not admit BTC. Any Devnet BTC test mint paired with BTC/USD remains a clearly labeled synthetic/unbacked test asset; a Devnet test mint is still a real on-chain SPL account but is not a claim of BTC backing. Localnet/simulator fixtures cannot substitute for CP5. A missing, stale, partial, wrong-feed, too-wide-confidence or depegged observation blocks new swaps/seed risk according to policy. S5 includes an ETF-specific fee/depth model; the old auction's S4A `NO_GO` result does not set AMM fees. Fees remain inside the corresponding pool custody balances; a cumulative fee ledger is informational accounting over those balances, not an additional asset or liability. The weighted invariant and share backing count each actual custody token once, including retained fees. Dynamic fees enter v1 only if the model selects an exact bounded function; otherwise use a reviewed fixed fee. A fee schedule or direction rule cannot be described as sandwich-proof or LVR-proof without adversarial evidence.

**Real trigger/settlement loop:** a permissionless `poke`/`check_rebalance` can read current pool balances and verified prices, update an eligibility/observation record, or open a bounded rebalance window. This is the accepted replacement for the blueprint's scheduled `rebalance()`-as-trade behavior: scheduling triggers eligibility/maintenance, not a swap. It cannot create a counterparty or move the portfolio by itself. Actual asset changes occur only in an atomic `swap_exact_in` (or equivalent) that receives real input tokens from a trader and pays real output tokens from the pool. Keep the swap callable without the scheduler so a crank outage cannot freeze eligible trades or exits. Helium Cron is the first recurring L1 candidate: it can schedule a compiled `poke` into a TukTuk queue, but the exact ETF job, schedule funding/stop/recovery, source/binary identity and external crank-turner execution still need proof. TukTuk's individual `Now`/`Timestamp` tasks remain one-shot; its return-data requeue is an alternative, not a requirement if Cron passes the exact proof. The checkpoint must reconcile a confirmed task invocation and show that a distinct trader-funded swap is still needed. MagicBlock ER is a different execution model; Hydra’s base-layer crank is a distinct, unselected L1 comparison candidate with an external cranker, and its Devnet deployment/source correspondence and ETF `poke` compatibility remain unverified; Antegen remains unproven for this deployment. Thus “no Coloyond-operated backend or personal bot” is a possible operations goal, while “zero off-chain infrastructure” and “automatic AMM trading” are not accepted architecture claims. Pyth update publishers, RPCs, scheduler crank-turners and traders remain external liveness dependencies.

**Share, fee and shutdown behavior:** v1 shares represent a pro-rata claim on actual pool custody assets under the formulas proposed in [the ETF v1 contract](../rebalancing/contracts/etf-v1.md). Initial shares use a documented USD-NAV denomination; later proportional deposits mint against the limiting asset ratio and atomically return unused inputs; redemptions floor each asset output, with full-supply redemption transferring all remaining balances. Retained AMM fees stay in those balances and are counted once. There is no separate ETF reserve, bounty balance or fee liability: a cumulative fee counter is informational and does not reduce backing. Direct token donations are already part of custody and therefore share backing; no sync instruction can count them twice. Withdrawal remains in-kind and permissionless under risk pause. No “up-only” or guaranteed rebalancing claim is allowed. S5A remains a draft. Existing S5B/C/D1/D2 results are candidate research and evidence against that draft, not implementation against an accepted revision. Their relevant findings must return as reviewed S5A amendments; S5E remains blocked until S5A and the required math/oracle/fee decisions are accepted.

**Orders:** the initial conditional rule is a *vault-level target change* with on-chain price predicate, not a claim that any trader's external limit order will fill. **Appended Sprint 10** adds a separate user order module that escrows the user's token in an `Order` PDA and allows any solver to fill at or better than the on-chain minimum exchange rate after an on-chain Pyth trigger; include partial-fill accounting, user cancellation, expiry and permissionless reclaim. Its settlement is separate from vault shares. Only after audited composition may a fill deposit output into a vault in the same transaction. This keeps “portfolio condition” and “personal order” semantics distinct and avoids routing private orders through a custodial API.

## 5. Off-chain automation that cannot override the chain

Two independent keeper deployments, on separate RPC providers and signing keys, observe vault accounts and the pinned Pyth feed accounts; a third party can run the same open-source binary. The sponsored push feeds are the primary price-updater path; self-operated permissionless Price Pushers are backups. Since the August 2026 Pyth Core upgrade, Hermes fetching requires an API key, so distribute that off-chain availability risk across operators and never make one key an on-chain authorization requirement. Each loop derives the next valid action from chain state, simulates it, submits with bounded fees, waits for confirmed/finalized status, and re-reads the sequence number. Use account subscriptions plus periodic full reconciliation; neither WebSocket nor an indexer is the source of truth. Restart from on-chain accounts, not a private queue. Key material belongs in a dedicated keeper signer, never in the APK or repository. Keys pay fees and receive only earned bounties. A public runbook and event/account decoder let other operators compete. [Pyth push feeds](https://docs.pyth.network/price-feeds/core/push-feeds/solana), [Pyth price-updater guidance](https://docs.pyth.network/price-feeds/core/use-real-time-data/pull-integration/solana).

The SDK is a **transaction builder**, not an autonomous scheduler: `observe_condition`/`activate_condition`/`start_rebalance`/`fill_auction`/`finish_or_expire` enforce eligibility. The keeper may use [Symmetry's `KeeperMonitor`](https://docs.symmetry.fi/guides/keeper) in a separate comparative Devnet pilot; its code is not silently wired to Coloyond's program. Availability target for our own Devnet pilot: with two healthy keepers and eligible price updates, 99% of triggerable transitions are submitted within five minutes; report p50/p95 delay, stale oracle incidents, failed landing, unfilled auction time and net outcome. This is an operating SLO, not a financial guarantee. If both keepers fail, the instruction remains callable by users and other solvers, and the UI shows “eligible, awaiting executor.”

| Economic safety | Benchmark fees earned, value leakage, bounty paid and keeper participation under realistic liquidity; stop/cap rules dominate optimistic yield claims. |

| Governance | Fee/asset/oracle policy uses in-program multisig + delay; the separate loader upgrade authority has an externally enforced on-chain delay/multisig or is revoked. ## 8. Decision gates and non-negotiable exclusions

1. **Sprint 0 architecture gate:** if the pinned Pyth feed or on-chain market lacks viable freshness/liquidity, reduce the initial asset universe or stop; do not make a centralized price/route API authoritative. Verify all advertised Devnet deployments directly before coding against them. Attempt the reviewed Reserve Folio controller route and reject it only on explicit failed compatibility/trust/fee criteria.
2. **Sprint 2 economic gate:** a fill must improve target drift without exceeding conservative price/NAV loss bounds. If solvers do not appear at safe prices, do not widen bounds automatically; extend/expire, display the stall and reconsider the incentive design.
3. **Sprint 4 fee gate:** pick v0.3.0 fee and reserve parameters from measured spread, oracle uncertainty, transaction cost and keeper competition. The previously quoted 50/50 and 70/30 examples are hypotheses, not inherited facts or defaults.
4. **Sprint 5 ETF gate:** freeze separate v1 program/account/IDL/identity contracts, verify each exact Devnet mint/feed, prove checked weighted math against reference vectors, and confirm real atomic SPL swaps. The scheduler adapter must be replaceable and must not be claimed autonomous. Literal zero-off-chain, guaranteed arbitrage, automatic self-balancing and “up-only” claims are rejected.
5. **Sprint 6 security gate:** no public mainnet custody for either protocol without independent version-specific review, verified deployment, `ProgramData` authority disclosure and independently enforced upgrade controls, reproducible tests, TVL cap and emergency exit drill. A verified build proves source correspondence, not safety. [Solana verified builds](https://solana.com/docs/programs/verified-builds).
6. **Sprint 7 Devnet gate:** the developer review runs only on Devnet test assets. It does not authorize Mainnet deployment or transactions. Any future funded release requires a separate plan and explicit authorization. No keeper uptime promise, principal guarantee, or “atomic whole rebalance” language.

The planned system does **not** assume a generic Solana cron, active Symmetry keepers, Jupiter Trigger V2 on-chain orders, liquid Symmetry share-token markets, Devnet support inferred from local tests, YieldBasis's leveraged economics, or automatic access to someone else's DEX fees.

## 9. Final independent recheck: stack, executable loop and changed decisions

**Decision update (11 October 2026):** the v0.3.0 Dutch-auction core remains unchanged for the existing two-asset flow. The colleague's multi-token weighted-mean AMM is now a second major foundation pillar, implemented as independent ETF v1 in Sprint 5; this changes the overall architecture and adds an AMM track, but does not replace or merge the auction implementation. The full source is preserved at [the original blueprint](blueprints/no-backend-auto-rebalancing-multi-token-etf-solana-devnet.md). The plan resolves its unsafe/unsupported assumptions explicitly: the sample arithmetic and swap bodies are illustrative, dynamic fees do not prove LVR/sandwich protection, the invariant is not an “up-only” guarantee, and a scheduler/crank-turner does not supply a swap counterparty. The scheduled-trade proposal is deliberately replaced by scheduled eligibility/maintenance plus distinct permissionless trader-funded swaps. This retains a no-project-backend goal without claiming automatic trading; third-party scheduler, oracle, RPC and trader availability remains off-chain. Helium Cron scheduling compiled TukTuk tasks is the leading recurring Devnet candidate, with bounded TukTuk requeue as an alternative; neither is selected until an exact ETF task executes. The pinned Cron 0.3.0 IDL is recorded, but the published `@helium/cron-sdk@0.1.1` metadata points to an older source `gitHead` and declares Anchor `^0.31.0`; package parity and this repo's Anchor compatibility remain unverified. Removing Cron records and closing the job does not cancel action `TaskV0` accounts already copied into TukTuk. Freeze a generation-guarded `scheduled_poke` and prove the stop sequence: disable/increment under the pool write lock, dequeue/read back all pending coordinator and action tasks using the queue authority, then remove records and close the job. Stale generations must no-op, including after re-enable. Hydra’s base-layer crank remains a separate unverified L1 comparison candidate; MagicBlock ER and Antegen are not frozen dependencies. The ETF v1 authority and fee-accounting model must be isolated and frozen before program implementation; they are not yet frozen. Existing fixed Pyth Receiver/Full checks, separate per-program manifests, and the old SDK comparison decisions remain.

**Concrete v0.3.0 loop:** a published WSOL/USDC vault observes on-chain drift, a permissionless caller starts a bounded auction, and an independent taker supplies the other leg in a confirmed atomic fill. Each fill obeys its oracle-relative loss budget and fee/reserve rules; anyone can finalize or users can redeem in kind without waiting for a bidder.

**Concrete ETF v1 loop:** a pool is initialized with exact admitted SPL mints, target weights, share mint, verified feed bindings and seed assets. Pyth account updates provide prices; a permissionless `poke` or external scheduler may record that an eligibility/maintenance condition is true. A separate trader wallet supplies input tokens to an atomic weighted-mean AMM swap and receives output from pool custody; fees are booked to the versioned pool ledger, and read-model weights update from confirmed account balances plus verified prices. If nobody trades, the portfolio composition does not move. If the scheduler is down, open swaps and withdrawals remain permissionless; if the oracle is stale, risk-increasing paths fail closed. Fees do not guarantee positive NAV and AMM invariant growth does not prove profit. Every displayed balance/price/weight is tied to RPC context, feed publish time and protocol revision.

**What remains unproven:** neither protocol is audited or ready for public custody. Devnet asset/feed admission, auction liquidity, ETF AMM math/transactions, scheduler execution, keeper uptime, Android funded-signing flow and verified upgrade authority remain open. The native Android card journey is unfinished beyond probes. Official documentation proves capabilities and constraints, not live integration. Sprint 0 and Sprint 5 must separately distinguish deployed programs, SDK availability, oracle freshness, executable market depth and external scheduler service. The former 13-week estimate is withdrawn and must be re-baselined for two protocol paths and the restored card product.
