# TukTuk and Cron Devnet account probe

Run `python3 tools/rebalancing/etf-scheduler-probe/probe.py` to read the current Devnet genesis, TukTuk and companion Cron program accounts and their loader-linked ProgramData accounts, config account and task queues. This standard-library probe is read-only. It decodes Anchor-discriminated config/queue accounts, queue bitmap occupancy, minimum crank reward and task-queue account lamports. It validates zero allocation padding, bitmap length and out-of-capacity task bits. For at most five active queues it inspects at most three occupied task IDs per queue using discriminator, queue and ID filters; the sample is therefore bounded to 15 task-account reads. The TaskV0 decoder recognizes `CompiledV0` versus `RemoteV0`, the `Now` and `Timestamp(i64)` triggers, compiled account/instruction indexes, signer-seed limits, description size and allocation padding. For each sampled task, it independently derives the expected address from `[b"task", task_queue, task_id.to_le_bytes()]` and fails if the RPC account key differs. The standard-library PDA helper is checked against six vectors generated by Solana's `solana-pubkey` 2.4.0. TukTuk individual `TriggerV0` tasks remain one-shot, while the separate Helium Cron program can schedule recurring compiled tasks into a TukTuk queue. The probe records each ProgramData deployment slot, upgrade authority, deployed-byte count and SHA-256 fingerprint. These point-in-time byte hashes do not prove correspondence with maintained source or a reproducible build. Both programs still depend on external crank-turner submissions, queue/cron funding and rewards; account presence does not prove recurrence, ETF compatibility, or an available executor. Remote URLs and signer keys are intentionally not printed. Account lamports include rent-exempt allocation; the probe does not call that amount spendable funding. Existing unrelated task payloads do not prove ETF compatibility, task execution, or an available external crank-turner. The probe does not create a task queue or submit any transaction.

Run local decoder tests with `PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s tools/rebalancing/etf-scheduler-probe -p 'test_*.py' -v`.

`cron_idl.py` validates the exact Helium Cron 0.3.0 IDL snapshot from the pinned
upstream revision and prints the selected instruction discriminators and ordered
account metas. `test_cron_idl.py` protects initialization, task registration,
recurring execution, recovery and close account surfaces. The pinned SDK wrapper
only builds the initializer; it does not wrap the complete lifecycle. In
particular, removing Cron records and closing a Cron job does not cancel action
tasks already materialized in TukTuk. A safe stop must disable the ETF scheduler
generation first, dequeue pending coordinator/action tasks with the queue
authority, then remove records and close the job; this full sequence still
requires an actual Devnet proof. The checked-in IDL and SDK metadata do not prove
that the deployed Cron binary matches the pinned source.

`payload_size.py` provides a separate, offline Borsh size estimate for hypothetical `CompiledV0` tasks from the maintained TukTuk field definitions. It validates `u8` account-index bounds, the decoder's maximum of 16 PDA seeds per signer and 32 bytes per seed, and reports serialized `TaskV0` account-data bytes, including a one-shot trigger, description, instruction data and optional signer-seed vectors. Its 40-byte description and `Now`/`Timestamp(i64)` trigger rules mirror current source. This is not TukTuk's queue instruction allocation formula: `queue_task_v0` reserves `8 + size_of::<TaskV0>() + transaction.size() + 4 + description.len() + 60`, and the maintained `CompiledTransactionV0::size()` heuristic excludes signer-seed vectors. The exact target allocation and serialization fit therefore remain unproven; do not use the Borsh estimate to infer rent or successful task creation. The estimate also does not choose ETF accounts, predict full Solana transaction size/compute, or prove scheduler compatibility. A separate `requeue_account_growth()` check models the maintained return-task allocation expression (`serialized TaskV0 body + 8-byte discriminator + 60-byte slack`) against Solana's 10,240-byte single-instruction account-growth ceiling. It only bounds one empty returned-task PDA's data growth and does not prove rent funding, queue solvency, or execution.

`returned_tasks.py` is an offline, strict Borsh parser for TukTuk's direct `RunTaskReturnV0` bytes plus a small constraint model for returned compiled children. It checks the 1,000-byte direct-return bound, exact consumption (no trailing bytes), enum/option tags, UTF-8, child description size, per-signer PDA seed limits (at most 16 seeds, each at most 32 bytes), parent-declared free-task capacity, supplied ID uniqueness/range/occupancy, child queue-capacity declaration, and the queue-minimum crank reward rule. It parses `RemoteV0` but rejects it in the no-backend candidate policy; it also rejects the alternate `tasks_accounts` path rather than implying that path is covered. Twenty-six tests cover the parser and deterministic checks, including maximum/malformed child signer-seed boundaries, child compiled-index bounds, offline supplied task-account PDA/order/emptiness fixtures, and a 166-byte source-shaped single-child requeue fixture. That fixture uses placeholder account keys/instruction bytes and the local Python Borsh builder; it is not the production ETF `poke` payload and is not serialized with Helium's Rust types. This remains an offline model: supplied PDA addresses and empty-account markers are fixture inputs, not RPC-verified account ownership or state. It does not verify the invoked program identity, queue or task lamports, rent, funding, CPI effects, stop policy, or any crank execution. No queue/task was created and no transaction was submitted.

Queue registration and automated invocation require a separately reviewed wallet-signed Devnet flow. Do not interpret this program-account probe as proof that a queue is funded, a task is valid, or any third party will execute it.

`cron_funding.py` is a parameter-only estimate of one Cron `queue_cron_tasks_v1`
pass. Supply the Cron balance and rent minimum, the queue minimum crank reward,
the job's action cap/outstanding records/empty records, and rent/current balances
for each used return PDA. The source emits one successor coordinator plus each
nonempty selected action record, with at most five action records per pass;
the Cron PDA funds `task_count * queue_min_crank_reward` and any return-PDA rent
deficit while keeping its own rent minimum. The calculator reports the exact
modeled threshold/shortfall, the rent actually paid in source order, and the
post-call Cron balance. If a later rent deficit fails, earlier PDA rent top-ups
may already be paid; if the reward check fails, rent top-ups remain paid but no
crank reward is transferred. Both paths stand down.
It has no Devnet defaults and excludes initial setup, task-queue deposit/capacity,
crankers' transaction fees, account-layout/serialization validity, and executor
availability. Rent and account-size inputs must come from actual reads and
serialized task construction before wallet approval. The values are not a
runtime liveness guarantee or an operating-cost recommendation.
