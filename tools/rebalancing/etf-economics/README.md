# ETF v1 fee and depth scenario model

Run `python3 tools/rebalancing/etf-economics/run.py` from the repository root. The generated `results.csv` is an ignored, reproducible **hypothetical** sensitivity table for a two-asset 50/50 weighted-mean pool at initial $1 oracle marks. It varies assumed pool depth, trade size, fixed fee, external price move, uncertainty haircut and transaction cost in both `output_appreciates` and `input_depreciates` directions (12,096 rows). The run also refreshes the tracked `dynamic_results.csv`: 1,728 bounded dynamic-fee rows, each compared with fixed 5/30/100 bps fees and their break-even moves. `depth_sweep_results.csv` adds 27 fixed-notional price-impact rows across three assumed depths, notionals and fees.

The candidate fee is 5 bps plus 10 bps for each full 100 bps of conservative move signal beyond a 25 bps deadband, capped at 100 bps. It is a test input only and uses the scenario's external-move assumption as its signal; it is not an adopted oracle/account-state rule. The uncertainty grid includes 3/4/10 bps values from a recorded Devnet snapshot (SOL and BTC passed the diagnostic age check, while USDC was stale), alongside synthetic 5/25/100 bps values. This was not a usable three-feed basket; these observations are neither a distribution nor an approved confidence policy. The model answers a narrow question: under those assumptions, when is a trader still paid enough to arbitrage the pool, and how does that profit correspond to the pool's mark-to-market loss? In the reverse direction it fixes input-token quantity at the initial $1 mark, so its actual entry value falls with the modeled input-price decline; it does not hold entry USD notional constant between directions. The separate depth sweep does hold the initial-mark trade notional constant. Nothing here is a market forecast, live depth observation, fee recommendation, LVR guarantee, or evidence of Devnet liquidity. The model does not include gas sponsorship, latency distributions, multi-hop routing, oracle update availability, competing trades, withdrawals, token depegs, or three-asset cross-pool effects. Final fee selection remains blocked on accepted S5B math, S5C oracle limits and real executable-depth evidence.

Run `python3 tools/rebalancing/etf-economics/quote_band_matrix.py` for separate candidate quote-band sensitivities over the generated 29,106-row moderate-reserve S5B corpus and the 60-row selected near-`u64` corpus. The script pins that input file's SHA-256 so a changed S5B corpus cannot silently produce stale comparison rows. It represents each marked value as the exact rational `amount * raw_price / 10^(decimals + exponent_magnitude)` and compares gross input with exact fee-adjusted output without intermediate USD rounding: `abs(output_usd - input_usd) / input_usd <= band_bps / 10,000`. The ratio includes curve impact and fee; it is not a standalone oracle confidence/deviation check. The pinned source contains one first-qualifying drift-improving input size per weight partition and ordered asset pair, so counts describe a selected finite corpus rather than all possible swaps or market frequency. The script writes one report per reserve corpus. Both are finite synthetic matrices, not live market data or an approved band; neither includes confidence intervals, update latency, route costs or transaction execution.

Run `python3 tools/rebalancing/etf-economics/three_asset_sensitivity.py` for a bounded three-asset candidate-math grid (576 CSV rows) and `python3 -m unittest discover -s tools/rebalancing/etf-economics/tests -p 'test_three_asset_sensitivity.py' -v` for its focused checks. Assumptions are 400 SOL / 0.8 BTC / 20,000 USDC at $100 / $50,000 / $1 marks and 40/40/20 weights; the BTC or SOL reserve remains present when another ordered pair is traded. The grid varies all six ordered pairs, input sizes of 1/10/50/100 bps of the input reserve, fees of 5/30/100 bps, relative moves of 0/25/100/500 bps, and both output-appreciates/input-depreciates directions. It uses `Decimal` precision 50 for weighted constant-mean exact-in candidate math. Trader PnL and pool marked-value change are opposing sides of one swap, excluding transaction costs. This is a finite hypothetical sensitivity only: it is not evidence of executable depth, selected fee or quote bands, approved policy, contract parity, or LP returns.

Run `python3 tools/rebalancing/etf-economics/weighted_delayed_mark_move.py` and its focused `test_weighted_delayed_mark_move.py` to compare fee-inclusive swap-leg marks under a small three-asset relative-price shock grid. The model reuses the candidate weighted quote for all six 40/40/20 SOL/BTC/USDC pairs and reports gross fee value separately. Its 324 rows use synthetic marks, reserves, fees and trade sizes; they do not model price-path latency, live depth, or a production policy. See [`s5d2-weighted-mark-move.md`](../../../docs/rebalancing/evidence/s5d2-weighted-mark-move.md) for assumptions and limits.

Run `python3 tools/rebalancing/etf-economics/oracle_confidence_sensitivity.py` and its focused `test_oracle_confidence_sensitivity.py` to replay all eight independent low/high price corners over the pinned 29,106-row S5B drift corpus. This is an endpoint sensitivity at labeled confidence-ratio values; it does not prove the property for every interior price, estimate probabilities, select confidence policy, or represent conservative Q96 runtime output. See [`s5d2-oracle-confidence-sensitivity.md`](../../../docs/rebalancing/evidence/s5d2-oracle-confidence-sensitivity.md).

Run `python3 tools/rebalancing/etf-economics/oracle_confidence_profile_sensitivity.py` and its focused `test_oracle_confidence_profile_sensitivity.py` to replay all eight independent low/high corners for three asymmetric observation-shaped confidence profiles and coordinatewise wider multiples. The pinned corpus has no per-row confidence metadata, so this is not historical replay; every result is candidate-only and does not prove continuous-box robustness or select policy. See [`s5d2-oracle-confidence-profile-sensitivity.md`](../../../docs/rebalancing/evidence/s5d2-oracle-confidence-profile-sensitivity.md).

Run `python3 tools/rebalancing/etf-economics/weighted_matched_notional_mark_move.py` and its focused `test_weighted_matched_notional_mark_move.py` to compare hypothetical three-asset trade/shock outcomes at the same pre-shock USD input notional across all six ordered pairs. The 648 rows remain candidate math and synthetic marks; they do not establish executable depth or program parity. See [`s5d2-weighted-matched-notional.md`](../../../docs/rebalancing/evidence/s5d2-weighted-matched-notional.md).

Run `python3 -m unittest discover -s tools/rebalancing/etf-economics/tests -p 'test_in_kind_floor_sensitivity.py' -v` for the separate integer-base-unit redemption floor check. It covers a 15-case synthetic grid over 6/8/9-decimal assets and `u64`-bounded reserve/share inputs; it does not model Token-2022 fees or claim program/CPI parity.

Run `python3 tools/rebalancing/etf-economics/redemption_sequence_sensitivity.py` and its focused `test_redemption_sequence_sensitivity.py` to compare one-shot partial exits with split burns under the draft floor formula. The 33-case synthetic grid covers three reserve scales, equal and unequal partial-burn schedules, and a split sequence ending in the exact full-exit rule. It reports per-asset payout shortfalls and remaining custody; it does not model Anchor/CPI behavior, transfer fees, transaction ordering, or holder fairness.
