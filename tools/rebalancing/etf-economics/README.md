# ETF v1 fee and depth scenario model

Run `python3 tools/rebalancing/etf-economics/run.py` from the repository root. The generated `results.csv` is an ignored, reproducible **hypothetical** sensitivity table for a two-asset 50/50 weighted-mean pool at initial $1 oracle marks. It varies assumed pool depth, trade size, fixed fee, external price move, uncertainty haircut and transaction cost in both `output_appreciates` and `input_depreciates` directions (12,096 rows). The run also refreshes the tracked `dynamic_results.csv`: 1,728 bounded dynamic-fee rows, each compared with fixed 5/30/100 bps fees and their break-even moves. `depth_sweep_results.csv` adds 27 fixed-notional price-impact rows across three assumed depths, notionals and fees.

The candidate fee is 5 bps plus 10 bps for each full 100 bps of conservative move signal beyond a 25 bps deadband, capped at 100 bps. It is a test input only and uses the scenario's external-move assumption as its signal; it is not an adopted oracle/account-state rule. The uncertainty grid includes 3/4/10 bps haircuts from one recent Devnet confidence observation, alongside synthetic 5/25/100 bps values. Those observations are neither a distribution nor an approved confidence policy. The model answers a narrow question: under those assumptions, when is a trader still paid enough to arbitrage the pool, and how does that profit correspond to the pool's mark-to-market loss? In the reverse direction it fixes input-token quantity at the initial $1 mark, so its actual entry value falls with the modeled input-price decline; it does not hold entry USD notional constant between directions. The separate depth sweep does hold the initial-mark trade notional constant. Nothing here is a market forecast, live depth observation, fee recommendation, LVR guarantee, or evidence of Devnet liquidity. The model does not include gas sponsorship, latency distributions, multi-hop routing, oracle update availability, competing trades, withdrawals, token depegs, or three-asset cross-pool effects. Final fee selection remains blocked on accepted S5B math, S5C oracle limits and real executable-depth evidence.

Run `python3 tools/rebalancing/etf-economics/quote_band_matrix.py` for a separate candidate quote-band sensitivity over the generated 29,106-row S5B three-asset corpus. The script pins that input file's SHA-256 so a changed S5B corpus cannot silently produce stale comparison rows. It screens whether gross input and exact fee-adjusted output values under the same normalized point marks satisfy `abs(output_usd - input_usd) / input_usd <= band_bps / 10,000`. The ratio includes curve impact and fee; it is not a standalone oracle confidence/deviation check. The pinned source contains one first-qualifying drift-improving input size per weight partition and ordered asset pair, so counts describe a selected finite corpus rather than all possible swaps or market frequency. It is a finite synthetic matrix, not live market data or an approved band; it does not include confidence intervals, update latency, route costs or transaction execution.
