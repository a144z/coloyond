# ETF client boundary

This package contains provisional S5F fixture validators, a live Devnet candidate-account reader, an RPC transaction-receipt reconciler, and a wallet submission lifecycle. The fixture corpus remains component-level rather than a complete snapshot contract. The wallet lifecycle checks the pinned Devnet genesis and transaction fee payer before signing, journals the signed signature before sending, sends one raw transaction with RPC retries disabled, and then reconciles only through RPC. Submitted, processed, timed-out, and otherwise unresolved signatures remain `unknown`; an unknown signature is retained for later RPC-only reconciliation. Manual retry is exposed only after a fresh RPC-confirmed rejection plus complete unchanged token-balance metadata. Callers must reuse one stable `operationId` for a logical action and provide `retryOfSignature` only for the latest verified rejection. The lifecycle requires a durable journal implementation with atomic compare-and-swap semantics; this package intentionally provides no browser storage or UI. The receipt path does not yet read ETF pool state, share supply, or on-chain fee counters. Transaction builders and pool-state reconciliation depend on the frozen S5E IDL.

The fixture document remains explicitly `fixtureOnly`, and the ETF deployment manifest, program ID, production fee/risk limits, and S5E IDL are not frozen. Keep unsupported or unavailable observations tagged with their reason; a failed snapshot cannot include oracle, balance or pool value payloads, while a stale oracle-only observation can retain diagnostic metadata. Preserve `u64`/`i64` values as decimal strings. Validators reject decimal strings whose digit length already exceeds the declared wire range before constructing a `BigInt`; required text fields use the same explicit Unicode White_Space set as the Python fixture validator, and both validators require integer strings to end immediately after the last digit. `unknown` wallet actions never authorize automatic resend. Receiver `Full` verification and fixed Push Feed account status remain distinct.

Run `npm test --prefix packages/etf-client` and `npm run typecheck --prefix packages/etf-client`. Do not add schema-generation or RPC dependencies before the program interface is frozen.

## ETF v1 client surface (S5F draft)

`src/manifest.ts` validates the exact generated IDL SHA-256 (UTF-8 `JSON.stringify` of the parsed IDL), Devnet genesis, canonical config hash, all program-owned PDA derivations, accepted math/oracle/fee fields, explicit synthetic-asset labels, the exact candidate mint/feed tuples, Receiver ownership, and fixed shard-0 Push PDA derivation. `verifyEtfManifest` rejects the draft local-build program ID. A verified context is immutable and is process-local; caller-created lookalikes are not accepted.

`src/readback.ts` provides `readEtfSnapshot(connection, verifiedManifest, { walletAddress })`. It confirms the Devnet genesis, executable upgradeable program, ProgramData binary hash and authority, pool/config/state/share mint, each underlying classic SPL mint's owner/layout/decimals/supply/authorities, each custody account and cumulative fee counter, wallet token/share balances, and Pyth `PriceUpdateV2` owner/layout/feed ID/Full level/freshness/confidence. Push-feed mode identifies only the fixed-PDA derivation path; both modes separately require Receiver ownership, the expected feed ID and `Full`. A snapshot is immutable and bound to the exact manifest context that produced it.

`src/instructions.ts` builds unsigned instructions for initialize, seed, proportional deposit, in-kind redemption, trader-funded weighted swap, pause, eligibility-only `poke`, and the delayed governance resume flow. It does not send transactions. Governance builders bind current roles to the verified pool-state PDA read from RPC, so a completed on-chain authority handoff does not require a new config manifest. Propose/cancel require the current governance signer; execute is permissionless but requires the pending proposal still belongs to current governance. Cancel follows the contract and permits current governance to cancel an old-authority proposal by its exact nonce. Resume builders also require an immutable RPC snapshot, exact pool/state identity and caller-supplied expected sequence; execute/cancel require the pending proposal nonce. Execute additionally requires the snapshot's confirmed RPC block time to have reached the on-chain `execute_after`; the program remains authoritative when the wallet submits. Seed, deposit, and swap require a fresh snapshot and accepted oracle policy; deposit/swap also require active, unpaused state; redemption remains available while risk is paused. `poke` has no custody, token-program or counterparty accounts. `src/shares.ts` mirrors S5B initial-share, proportional-deposit and in-kind-redemption integer formulas and is checked against the Rust full-width vector corpus. Weighted swap quoting itself remains the Rust/on-chain implementation; this module does not approximate it.

### Manual wallet/RPC sequence once an admitted deployment exists

1. Load the reviewed accepted manifest and the IDL generated from the deployed program build. Confirm its exact SHA-256s, Devnet genesis, ProgramData authority, pool PDA, share mint, WSOL/Test-USDC candidate mints and exact Pyth feed accounts. Keep the Test-USDC candidate visibly labeled synthetic/unbacked.
2. Connect a Devnet wallet. Read the RPC genesis and call `readEtfSnapshot`; verify the displayed wallet, pool and mints match the connected wallet and reviewed profile. Do not proceed if any feed is not Receiver-owned, Full, identity-matched, fresh and inside the accepted confidence/exponent policy.
3. Build `initialize_pool` and sign it in the wallet. Re-read the pool and verify confirmed signature, initialized PDAs, config bytes/hash and pool state through RPC.
4. Create the wallet's idempotent share-token account with `buildCreateEtfTokenAccountInstruction` if readback shows it is missing, then reconcile it. Initialization starts paused. From a confirmed snapshot, current governance builds `buildProposeResumeInstruction` using the snapshot sequence and signs it. Re-read after confirmation. Once confirmed RPC block time reaches the stored `executeAfter`, any wallet can build `buildResumeRiskAfterDelayInstruction` with the pending nonce and current sequence, then sign it. Re-read and confirm the pool is unpaused before building the bounded seed from a newer snapshot. Reconcile each confirmed signature and the resulting pool/custody/share state before showing success.
5. For deposit, call `quoteProportionalDeposit` with the same RPC reserves and share supply; pass the same `maxInputs` and a user-selected positive `minSharesOut` no greater than the quote's shares to the builder. The on-chain S5B formula determines exact consumed amounts/refunds. Sign and reconcile wallet input balances, custody, refunds and share supply from RPC.
6. For a swap, use a distinct trader wallet and compute the quote using the reviewed S5B weighted math path. The trader signs and funds the `amountIn`; verify fee and out amount separately from the confirmed RPC account deltas. An eligibility `poke` never provides swap input or changes custody.
7. While risk is paused, build `redeem_in_kind` from the refreshed snapshot, sign, then reconcile burned shares, every returned asset amount, fees and the transaction fee from confirmed RPC metadata.
8. If a send is submitted or times out, keep the result unresolved and reconcile that signature through RPC before offering any retry. A rejected-transaction fee is displayed separately; verify every tracked token/share account is unchanged before a manual retry.

This package has not been connected to the project app shell and has not sent a Devnet transaction. Governance builders are covered by deterministic mocked-RPC tests only; no signed Localnet or Devnet proposal, delayed execution, or cancellation is proven. The deployment/program identity, current S5A economic and oracle policy, and admission proofs remain gates. Tests use candidate IDs and never synthesize wallet signatures or success receipts.
